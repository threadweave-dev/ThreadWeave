# RFC100 — Python Runtime

**Status:** Draft

**Version:** 1.0

---

# Abstract

This RFC defines the philosophy, responsibilities and public API of the ThreadWeave Python Runtime.

The Python Runtime is **not** a distributed execution engine.

It is a language adapter built on top of the ThreadWeave Execution Protocol.

Its purpose is to expose a natural Python API while delegating orchestration, scheduling, retries, resource allocation and supervision to the ThreadWeave Core.

This RFC intentionally focuses on the developer experience rather than implementation details.

---

# Relationship with the Core

The Python Runtime is one implementation of a ThreadWeave Runtime.

It communicates exclusively through the Execution Protocol.

The Core never executes Python code.

The Runtime never performs orchestration.

Responsibilities are strictly separated.

```text
Python Application
        │
        ▼
Python Runtime
        │
Execution Protocol
        │
        ▼
ThreadWeave Core
        │
        ▼
Worker
        │
        ▼
Python Executor
        │
        ▼
User Code
```

---

# Goals

The Python Runtime MUST:

- provide an idiomatic Python API;
- support both synchronous and asynchronous applications;
- integrate naturally with asyncio;
- expose distributed execution using familiar Python abstractions;
- hide infrastructure concerns;
- remain fully compatible with the ThreadWeave Execution Protocol.

---

# Non Goals

The Python Runtime is not responsible for:

- scheduling;
- retries;
- broker communication;
- resource allocation;
- worker discovery;
- execution placement;
- cluster management;
- observability.

Those responsibilities belong to the ThreadWeave Core.

---

# Design Principles

## Python First

The Runtime should feel like a native Python library.

Developers should think about Python functions.

Not distributed systems.

---

## Async First

Every operation performing I/O MUST expose a native asynchronous API.

This includes:

- Job submission;
- artifact upload;
- artifact download;
- result retrieval;
- status retrieval;
- cancellation;
- event streaming;
- log streaming.

The Runtime MUST never block the asyncio event loop.

---

## Sync is a First-Class Citizen

Many Python applications remain synchronous.

Examples include:

- Django
- Flask
- Click
- management commands
- scripts

The Runtime MUST provide equivalent synchronous APIs.

---

## Job-Centric API

Distributed execution revolves around Jobs.

The Runtime exposes Job objects.

Not Result containers.

A Job represents an execution request.

A Result is only one aspect of a Job.

Preferred:

```python
job = resize.submit(image)
```

Not:

```python
result = resize.delay(image)
```

---

## Distributed Execution Should Feel Like Asynchronous Execution

The Runtime should minimise the conceptual difference between:

```python
await http.get(...)
```

and

```python
await job
```

Distributed execution should integrate naturally into Python's async programming model.

---

# Application

Applications register Tasks.

```python
from threadweave import Application

app = Application("documents")
```

Applications define:

- Task registry
- configuration
- serialization
- middleware
- connection to ThreadWeave

---

# Tasks

Tasks are declared using decorators.

Synchronous Tasks:

```python
@app.task
def resize(image):
    ...
```

Asynchronous Tasks:

```python
@app.task
async def extract_text(document):
    ...
```

The Core makes no distinction.

Only the Python Executor understands Python callables.

---

# Job Submission

Submitting a Job waits only until the ThreadWeave Core has durably accepted the Job.

It never waits for execution.

---

## Synchronous

```python
job = resize.submit(image)
```

---

## Asynchronous

```python
job = await resize.asubmit(image)
```

The asynchronous API should be used whenever submission may involve I/O.

Examples include:

- artifact upload;
- serialization;
- network communication;
- daemon communication.

---

# Job

A Job is the central object exposed by the Runtime.

Example:

```python
job.id

job.status()

job.result()

job.cancel()

job.events()

job.logs()
```

Async equivalents:

```python
await job.astatus()

await job.aresult()

await job.acancel()

async for event in job.aevents():
    ...

async for line in job.alogs():
    ...
```

---

# Awaitable Jobs

Jobs SHOULD be awaitable.

```python
job = await train.asubmit(dataset)

model = await job
```

Equivalent to:

```python
model = await job.aresult()
```

Awaiting a Job suspends the coroutine.

It never blocks the event loop.

---

# Nested Jobs

Tasks may submit additional Tasks.

Example:

```python
@app.task
async def pipeline(dataset):

    preprocess = await preprocess_data.asubmit(dataset)

    cleaned = await preprocess

    training = await train_model.asubmit(cleaned)

    return await training
```

Nested Jobs are ordinary Jobs.

The Runtime does not distinguish them.

The ThreadWeave Core may record parent-child relationships between Executions for observability.

---

# Resources

Resources are declared.

Never allocated manually.

Example:

```python
job = await train_model.asubmit(
    dataset,
    resources={
        "cpu": 8,
        "memory": "32GiB",
        "gpu": 1,
    },
)
```

The Runtime validates.

The Core decides placement.

---

# Artifacts

Large data should be transported using Artifacts rather than embedded directly inside Job payloads.

Example:

```python
dataset = await app.artifacts.upload(
    "./dataset.parquet"
)

job = await train_model.asubmit(dataset)
```

The Runtime is responsible for:

- uploading Artifacts;
- creating Artifact references;
- replacing Python objects by protocol references.

The Core only receives Artifact identifiers.

---

# Errors

Remote exceptions should behave like Python exceptions whenever possible.

Example:

```python
try:
    await job

except FileNotFoundError:
    ...
```

The Runtime reconstructs Python exceptions from protocol messages.

---

# Runtime Responsibilities

The Python Runtime is responsible for:

- Task registration;
- Task discovery;
- argument validation;
- serialization;
- artifact handling;
- communication with the Core;
- exposing synchronous APIs;
- exposing asynchronous APIs;
- reconstructing Python exceptions.

The Runtime never performs orchestration.

---

# API Philosophy

The Runtime should make distributed execution feel natural.

Instead of:

```python
result = task.delay(...)

value = result.get()
```

ThreadWeave promotes:

```python
job = await task.asubmit(...)

value = await job
```

or

```python
job = task.submit(...)

value = job.result()
```

The developer manipulates Jobs.

Not broker primitives.

# Summary

The Python Runtime exists to make distributed execution feel like ordinary Python programming.

Developers write Python.

Tasks become Jobs.

Jobs behave like asynchronous computations.

The Runtime adapts Python to the ThreadWeave protocol.

The ThreadWeave Core orchestrates everything else.
