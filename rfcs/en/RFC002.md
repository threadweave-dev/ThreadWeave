# RFC002 — Overall Architecture

**Status:** Foundational
**Version:** 1.1

---

# Purpose

This RFC defines the high-level architecture of ThreadWeave.

It identifies the core components of the platform, their responsibilities, and the boundaries between them.

It intentionally avoids implementation details, protocols, deployment topologies, and algorithms. Those concerns belong in dedicated RFCs.

The objective is to ensure that every future feature fits naturally into the same architecture without weakening the separation between orchestration, scheduling, transport, and execution.

---

# Architectural Principles

The architecture follows the principles established in RFC000.

In particular:

* the Core is language agnostic;
* orchestration and execution are strictly separated;
* scheduling is separate from lifecycle orchestration;
* every subsystem is replaceable behind a stable contract;
* Resources and Capabilities are first-class concepts;
* important state transitions produce Events;
* failure domains must remain isolated;
* logical components must not imply a mandatory deployment topology.

# Core Components

## 1. Core Interface

The Core Interface is the protocol-facing boundary through which clients, SDKs, administrative tools, and external systems interact with ThreadWeave.

It supports operations such as:

* submitting Jobs;
* cancelling Jobs or Executions;
* inspecting Job and Execution state;
* retrieving Results;
* registering or inspecting cluster participants;
* subscribing to Events;
* querying platform metadata.

The Core Interface is a logical boundary, not a required deployment component.

It may be exposed through:

* local inter-process communication;
* a Unix domain socket;
* a network service;
* an embedded interface;
* another protocol-compatible transport.

The Core Interface may validate authentication, authorization, message structure, and compatibility requirements.

It does not:

* make scheduling decisions;
* own execution lifecycle policies;
* execute user code;
* implement language-specific Task semantics.

---

## 2. Orchestration Core

The Orchestration Core owns the lifecycle of Jobs and Executions.

It is responsible for:

* validating Commands;
* enforcing Job and Execution state transitions;
* determining when a Job becomes eligible for execution;
* creating Execution attempts;
* applying retry policies;
* applying timeout and cancellation policies;
* coordinating recovery after failures;
* requesting scheduling decisions;
* coordinating resource reservations;
* recording authoritative state transitions;
* emitting lifecycle Events.

The Orchestration Core decides whether an Execution should exist.

It does not decide the detailed placement of that Execution.

It does not execute user code.

---

## 3. Scheduler

The Scheduler produces scheduling decisions for eligible Executions.

It decides when and where an eligible Execution may run according to the scheduling information made available to it.

Its inputs may include:

* priority;
* required Resources;
* required Capabilities;
* placement constraints;
* affinity and anti-affinity rules;
* quotas;
* fairness policies;
* cluster capacity;
* reservations;
* locality information;
* scheduling deadlines.

Its outputs may include:

* a selected Worker or Executor;
* a resource reservation proposal;
* a deferred scheduling decision;
* an unschedulable decision with a reason.

The Scheduler may be responsible for:

* prioritization;
* placement decisions;
* fairness;
* load distribution;
* queue selection;
* admission decisions;
* scheduling-related preemption.

The Scheduler is not responsible for:

* creating retries;
* owning the Job state machine;
* executing user code;
* persisting authoritative Job state;
* transporting execution messages;
* supervising Executor processes.

Retry and backoff policies belong to orchestration.

The Scheduler only determines placement and dispatch eligibility for work that already exists.

---

## 4. Resource Manager

The Resource Manager maintains the platform view of available, reserved, allocated, and consumed Resources.

Examples of Resources include:

* CPU;
* memory;
* GPU capacity;
* TPU capacity;
* FPGA capacity;
* storage capacity;
* network bandwidth;
* consumable software licenses;
* custom quantitative resources.

The Resource Manager may also maintain information about Capabilities advertised by Workers and Executors.

Examples of Capabilities include:

* supported runtimes;
* operating system;
* processor architecture;
* CUDA availability;
* installed software;
* framework versions;
* hardware features;
* custom qualitative properties.

Tasks and Jobs declare Resource and Capability requirements.

Workers and Executors advertise available Resources and Capabilities.

The Resource Manager supports operations such as:

* registration;
* reservation;
* allocation;
* release;
* reconciliation;
* capacity reporting;
* resource accounting.

Scheduling decisions should depend on declared Resources, Capabilities, and placement constraints rather than hard-coded Worker identities.

Explicit Worker selection may still be supported as a placement constraint, but it is not the default scheduling model.

---

## 5. Broker Interface

The Broker Interface is the transport abstraction used for reliable delivery of Commands and execution-related messages between ThreadWeave components.

Its responsibilities may include:

* reliable delivery;
* acknowledgement;
* queueing;
* redelivery;
* back-pressure;
* message visibility;
* routing;
* ordering guarantees when supported;
* delivery guarantees;
* dead-letter handling.

Possible Broker implementations include:

* Redis;
* PostgreSQL;
* NATS;
* RabbitMQ;
* Kafka;
* an in-memory transport;
* a custom implementation.

The Core interacts with the Broker only through an abstract contract.

A Broker implementation does not define Job or Execution semantics.

It transports messages but does not decide what those messages mean.

The Broker may share physical infrastructure with the Event Bus, but their logical contracts remain distinct.

---

## 6. Worker

A Worker is a process responsible for supervising assigned Executions.

A Worker:

* registers with the cluster;
* advertises the Resources and Capabilities available through its Executors;
* receives Execution assignments;
* validates that an assignment can be accepted;
* starts and supervises Executors;
* reports lifecycle Events and telemetry;
* propagates cancellation and termination requests;
* detects Executor failures;
* handles graceful draining and shutdown;
* reconciles its local execution state with the Core.

A Worker may supervise one or more Executor instances.

A Worker does not:

* make global scheduling decisions;
* create retries;
* own the Job lifecycle;
* reinterpret orchestration policy;
* expose language-specific developer APIs.

A Node is the infrastructure host or execution environment on which one or more Workers may run.

A Node may represent:

* a physical machine;
* a virtual machine;
* a container host;
* a Kubernetes node;
* an edge device;
* another infrastructure boundary.

Node and Worker are distinct concepts.

---

## 7. Executor

An Executor is an execution component that runs user code for a specific runtime or execution format.

Examples include:

* Python Executor;
* JavaScript Executor;
* Java Executor;
* WASM Executor;
* container Executor;
* native process Executor.

An Executor is responsible for:

* receiving an Execution assignment from its Worker;
* resolving the referenced Task implementation;
* preparing the execution environment;
* deserializing inputs;
* invoking user code;
* reporting progress;
* propagating application failures;
* serializing outputs;
* returning an execution outcome;
* releasing execution-local resources.

An Executor may provide:

* process isolation;
* interpreter isolation;
* container isolation;
* environment preparation;
* sandboxing;
* runtime-specific diagnostics.

An Executor does not:

* schedule Jobs;
* select its own workload;
* create new Execution attempts;
* own retry policy;
* allocate cluster-wide Resources;
* mutate authoritative platform state directly.

Executors execute.

The Core orchestrates.

---

## 8. Language SDK

A Language SDK provides the developer-facing ThreadWeave API for a programming language.

Examples include:

* Python;
* JavaScript or TypeScript;
* Java;
* Go;
* Rust.

A Language SDK may be responsible for:

* Task declaration;
* Task registration metadata;
* Task discovery conventions;
* Job submission;
* Job and Execution inspection;
* Result retrieval;
* cancellation requests;
* Event subscriptions;
* argument validation;
* language-specific serialization;
* developer-friendly error handling.

A Language SDK communicates with ThreadWeave through the Core Interface.

It does not:

* perform orchestration;
* select Workers;
* allocate cluster Resources;
* execute remote user code;
* bypass protocol contracts.

A Language SDK and an Executor may be distributed as part of the same language integration project, but they remain separate architectural roles.

For example, the ThreadWeave Python distribution may contain both:

* a Python SDK used by application developers;
* a Python Executor used by Workers.

---

## 9. Event Bus Interface

The Event Bus Interface is the logical publication and subscription contract for Events.

Every authoritative state transition must produce an Event.

Examples include:

* JobCreated;
* JobQueued;
* ExecutionCreated;
* ExecutionScheduled;
* ExecutionStarted;
* ExecutionProgressed;
* ExecutionSucceeded;
* ExecutionFailed;
* RetryScheduled;
* WorkerRegistered;
* WorkerDisconnected;
* ResourceReserved;
* ResourceReleased.

The Event Bus may support:

* publication;
* subscriptions;
* filtering;
* consumer groups;
* replay;
* retention;
* durable consumption;
* external integrations.

The Event Bus does not require a separate physical infrastructure component.

A single system such as Kafka, NATS, Redis, RabbitMQ, or PostgreSQL may implement both Broker and Event Bus contracts.

The contracts remain distinct:

* the Broker transports Commands and execution-related messages;
* the Event Bus distributes immutable facts that have already occurred.

Events do not express intent.

They record facts.

---

## 10. State Management and Storage

State Management owns the authoritative representation of ThreadWeave state.

Storage provides the persistence mechanisms used by State Management and other subsystems.

Persisted information may include:

* Job metadata;
* Execution history;
* Task identities and metadata;
* Results;
* retry information;
* Events;
* Artifacts and Artifact references;
* resource reservations;
* scheduler metadata;
* cluster membership;
* Worker leases;
* compatibility metadata.

Storage backends are replaceable.

Possible implementations may include:

* relational databases;
* key-value stores;
* distributed logs;
* object storage;
* embedded databases;
* in-memory storage;
* combinations of multiple systems.

Events are immutable records of facts.

ThreadWeave may persist authoritative materialized state separately from its event history.

This RFC does not require complete event sourcing.

The exact consistency model, transaction boundaries, reconciliation strategy, and persistence guarantees belong in dedicated RFCs.

---

## 11. Artifact Management

Artifact Management handles data that should not be embedded directly in ordinary execution messages or Results.

Examples include:

* files;
* model checkpoints;
* generated reports;
* images;
* datasets;
* archives;
* large binary outputs;
* intermediate pipeline data.

Artifact Management may provide:

* upload;
* download;
* content addressing;
* metadata;
* lifecycle management;
* access control;
* retention;
* deduplication;
* integrity verification.

Jobs, Executions, Results, and Events may contain Artifact references.

Artifact Management is optional from the perspective of a deployment, but it is a first-class architectural capability.

The Core must not require one specific Artifact backend.

---

## 12. Observability

Observability is a built-in architectural capability rather than an afterthought.

The platform may expose:

* metrics;
* structured logs;
* distributed traces;
* execution history;
* event streams;
* resource utilization;
* scheduling decisions;
* queue depth;
* retry information;
* Worker health;
* Executor diagnostics.

Every subsystem contributes observability data.

Observability data must not become the authoritative source of platform state.

The absence or failure of an observability backend must not corrupt orchestration state or prevent safe execution, unless explicitly required by deployment policy.

# Execution Flow

A typical execution follows these logical steps.

```text
Application
    │
    │ Task invocation or explicit submission
    ▼
Language SDK
    │
    │ SubmitJob Command
    ▼
Core Interface
    │
    ▼
Orchestration Core
    │
    │ Validate Job
    │ Persist initial state
    │ Emit JobCreated
    │ Determine execution eligibility
    │ Create Execution
    ▼
Scheduler
    │
    │ Evaluate Resources, Capabilities,
    │ priorities and placement constraints
    ▼
Resource Manager
    │
    │ Reserve required Resources
    ▼
Orchestration Core
    │
    │ Confirm scheduling decision
    │ Emit ExecutionScheduled
    ▼
Broker
    │
    │ Deliver Execution assignment
    ▼
Worker
    │
    │ Accept and supervise assignment
    ▼
Executor
    │
    │ Load Task implementation
    │ Deserialize arguments
    │ Execute user code
    ▼
User Code
    │
    │ Return value, failure,
    │ progress or Artifact references
    ▼
Executor
    │
    │ Serialize execution outcome
    ▼
Worker
    │
    │ Report lifecycle and outcome
    ▼
Orchestration Core
    │
    │ Validate transition
    │ Persist Result and state
    │ Release Resources
    │ Apply retry or completion policy
    │ Emit Events
    ▼
Language SDK
    │
    ▼
Application
```

This flow is logical rather than prescriptive.

Implementations may optimize or combine steps, provided that architectural responsibilities and protocol guarantees remain intact.

# Failure and Retry Flow

Retries are owned by the Orchestration Core rather than the Scheduler or Executor.

```text
Execution fails
      │
      ▼
Worker reports outcome
      │
      ▼
Orchestration Core validates failure
      │
      ├── Retry policy allows another attempt
      │          │
      │          ▼
      │    Create new Execution
      │          │
      │          ▼
      │    Request new scheduling decision
      │
      └── Retry policy exhausted
                 │
                 ▼
          Complete Job as failed
```

Each retry creates a new Execution.

An Execution is never restarted in place after reaching a terminal state.

# Logical and Physical Architecture

The components described in this RFC are logical roles.

This RFC does not require a one-service-per-component architecture.

A small local deployment may run several components within one process:

```text
threadweave node
    ├── Core Interface
    ├── Orchestration Core
    ├── Scheduler
    ├── Resource Manager
    ├── in-memory Broker
    ├── Worker
    └── Executor
```

A distributed deployment may separate them:

```text
Control Plane
    ├── Core Interface replicas
    ├── Orchestration Core replicas
    ├── Scheduler participants
    ├── Resource Manager
    └── State Management

Data Plane
    ├── Worker A
    │     └── Executors
    ├── Worker B
    │     └── Executors
    └── Worker C
          └── Executors
```

The exact deployment topology, leader election model, replication strategy, and high-availability design belong in dedicated RFCs.

# Responsibility Boundaries

## Orchestration Core vs Scheduler

The Orchestration Core decides:

* whether a Job is eligible to run;
* whether a new Execution attempt must be created;
* whether a retry is allowed;
* whether a timeout or cancellation applies.

The Scheduler decides:

* where an eligible Execution should run;
* when capacity permits dispatch;
* which placement best satisfies policy and constraints.

---

## Scheduler vs Resource Manager

The Scheduler evaluates possible placements.

The Resource Manager owns Resource accounting, reservation, allocation, and release.

The Scheduler may request a reservation.

It must not independently mutate authoritative Resource state.

---

## Worker vs Executor

The Worker supervises execution infrastructure.

The Executor invokes user code.

The Worker owns:

* assignment acceptance;
* Executor lifecycle;
* cancellation propagation;
* local reconciliation;
* reporting to the Core.

The Executor owns:

* Task resolution;
* input deserialization;
* user-code invocation;
* output serialization;
* runtime-specific execution behavior.

---

## Broker vs Event Bus

The Broker transports operational messages.

The Event Bus distributes immutable Events.

A Command may be rejected.

An Event records a fact that has already occurred.

The same infrastructure may implement both roles, but their contracts must not be conflated.

---

## Language SDK vs Executor

The Language SDK is used by developers and applications.

The Executor is used by Workers to run Task implementations.

They may share:

* serialization libraries;
* Task identity conventions;
* protocol schemas;
* package metadata.

They must not share architectural responsibility.

---

# Design Constraints

Every future component must satisfy the following constraints.

## Single Primary Responsibility

Each logical component has one primary architectural responsibility.

Implementations may combine multiple logical components, but the boundaries between their responsibilities must remain explicit.

---

## Replaceability

No implementation is mandatory unless explicitly standardized by a later foundational RFC.

Every subsystem must be replaceable behind a stable contract.

Replaceability does not mean that every implementation provides identical optional features.

Mandatory and optional capabilities must be discoverable.

---

## Language Independence

The Core must not depend on application-language semantics.

The Core may understand:

* protocol messages;
* Task identities;
* Resource requirements;
* Capability requirements;
* Job and Execution state;
* scheduling constraints;
* Result and Artifact references.

The Core must not require:

* importing user application code;
* loading language-specific packages;
* interpreting language-native exceptions;
* embedding a specific application runtime.

Only Language SDKs, Executors, and language-specific tooling may depend on language semantics.

---

## Event-Producing State Transitions

Every authoritative state transition must produce an Event.

Components may use direct request-response communication where appropriate.

ThreadWeave is event-producing and event-observable, but this RFC does not require every interaction to be implemented as asynchronous event publication.

Commands express intent.

Events record facts.

---

## Resource-Oriented Scheduling

Scheduling decisions should depend on declared Resources, Capabilities, policy, and placement constraints rather than implicit Worker identities.

Worker identities may be used for:

* diagnostics;
* reconciliation;
* explicit affinity;
* administrative controls;
* targeted recovery.

They are not the default Task routing mechanism.

---

## Failure Isolation

A failure inside one Executor must not compromise:

* the Core;
* the Worker supervisor;
* unrelated Executors;
* unrelated Jobs;
* authoritative cluster state.

The required isolation mechanism may depend on the Executor type and deployment policy.

Possible mechanisms include:

* processes;
* containers;
* virtual machines;
* sandboxed runtimes;
* operating-system isolation.

---

## Protocol-Mediated Boundaries

Interactions between independently deployable components must occur through explicit, versioned contracts.

Components must not depend on undocumented internal behavior from another subsystem.

The exact protocol, compatibility rules, and transport bindings belong in dedicated RFCs.

---

## Reconciliation

Distributed state cannot rely exclusively on transient messages.

Workers, Executors, Resources, and orchestration state must be reconcilable after:

* process crashes;
* network partitions;
* message redelivery;
* duplicate delivery;
* delayed delivery;
* Core failover;
* Worker restart.

Detailed reconciliation rules belong in dedicated RFCs.

---

## Idempotency

Commands and lifecycle reports may be delivered more than once.

Components must be designed so that duplicate delivery does not produce invalid state transitions or duplicate logical Executions.

The exact idempotency keys and message semantics belong in the Execution Protocol RFC.

---

# Extension Boundaries

ThreadWeave is designed to support replaceable implementations of architectural contracts.

Potential extension categories include:

* Scheduler;
* Broker;
* Event Bus;
* Storage backend;
* Artifact backend;
* Executor;
* Language SDK;
* Resource provider;
* Capability provider;
* observability exporter;
* authentication provider;
* authorization provider.

An extension must not bypass the Orchestration Core to mutate authoritative Job or Execution state.

An extension must interact through the contract associated with its architectural role.

The general extension model, discovery mechanism, lifecycle, compatibility rules, and capability negotiation belong in RFC003.

# Summary

ThreadWeave is composed of independent logical components with explicit responsibilities.

The Core Interface exposes the platform through protocol-defined operations.

The Orchestration Core owns Job and Execution lifecycles.

The Scheduler produces placement and dispatch decisions.

The Resource Manager owns Resource accounting and reservations.

The Broker transports operational messages.

The Event Bus distributes immutable facts.

Workers supervise assigned Executions.

Executors run user code.

Language SDKs expose developer-friendly APIs without performing orchestration.

State Management preserves authoritative platform state.

Artifact Management supports large and external execution data.

Observability makes every subsystem inspectable.

The Core orchestrates.

The Scheduler places.

Workers supervise.

Executors execute.

This separation enables scalability, replaceability, language independence, failure isolation, and long-term maintainability.
